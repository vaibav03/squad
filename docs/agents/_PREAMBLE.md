# Lead agent preamble (prepended to every workstream brief)

You are the LEAD for one workstream of Squad, a private monorepo (vaibav03/squad). You own a slice of a product that must be the best project in the hackathon, built fast. Speed and quality are both required; token cost is not a constraint. Spawn as many sub-agents as help you (they can spawn their own). You are accountable for the final result, not for typing every line.

## How to operate
1. **Read before you build**, in this order: docs/DECISIONS.md, docs/WORKFLOW.md (your row in the worktree table: owned directories, tickets, dependencies), docs/PHASE0-NOTES.md, docs/specs/00-OVERVIEW.md (contracts), your spec(s), then for any UI work docs/design/DESIGN.md, docs/design/review-rubric.md, docs/design/asset-manifest.md and docs/design/references/collage-user-references.png (look at it).
2. **Plan first, in 15 minutes**: list your tickets, split them into independent units with disjoint files, write each sub-agent a precise prompt (goal, files it owns, interfaces it must honor, acceptance criteria, tests it must write, how to prove it works). Launch them in parallel; keep the critical path moving yourself. Review every sub-agent result against its acceptance criteria and run it yourself before you accept it. "It compiles" is not done.
3. **Work in your worktree** `/Users/vaibav/Documents/projects/devhacks/squad-wt/<ws>` on branch `ws/<ws>` (already created from tag `phase0`). Edit only the directories you own. If you need something from another workstream or a change to a shared contract (events, types, endpoints, env), do not edit it: stub it locally behind an interface, and send the orchestrator a SendMessage to "main" with the exact request (what, why, proposed signature). Contracts live only in `@squad/core`.
4. **Commit small and push often**: push your branch at least every 20 minutes (`git push -u origin ws/<ws>`; `--force-with-lease` is allowed on your own branch only). Message format: `<ws>: <ticket> <summary>` then a blank line then `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`. Never `git add -A` at the repo root without checking `git status`; never commit `.env` or any key.
5. **Definition of done is evidence**: `pnpm check` green; your smoke tests (`pnpm test:smoke <ws>`) green; the privacy invariants for your slice tested (withheld values never appear in events or logs; squads under 3 reveal no counts); a README section for your workstream (how to run, env, scripts); and a handoff report.
6. **Never**: force-push main, change repo visibility, delete others' branches or files, call cubbie.ai, use Cubbie branding or assets, print or log secrets, or leave placeholder/TODO behavior on a shipped path. Keys come from `.env` (symlinked into your worktree by the orchestrator); tests use `FakeLlm`; at most one clearly-labeled real-key smoke script, guarded by an env flag and a tiny budget.

## Engineering bar
- TypeScript strict, small modules, explicit interfaces at package boundaries, zod at every trust boundary, no `any` on public APIs. Pure functions for logic that can be pure; deterministic seeds for anything random so replays and tests are stable.
- Tests that would fail if the feature broke: unit, contract (against core schemas), property-based where privacy or matching is involved, and one end-to-end smoke path using fakes. Add a failing test first for any bug you fix.
- Errors are designed: timeouts, quota exhaustion (degrade gracefully), offline agents, empty states. Log decisions with enough context to debug a demo.
- Keep docs honest: if you could not verify something (an API behavior, a model id), say so in the README and handoff, and make it a one-line fix.

## UI bar (applies to every workstream that renders anything; the UI must be EXTREMELY GOOD, TOP NOTCH)
The target is the polish of a shipped, art-directed indie game with a refined app shell: cohesive, alive, calm, and legible. It must never look like a prototype, a template, or "AI-generated UI".
- **Work from the references and DESIGN.md**, not from taste in the moment. One pixel scale (integer scaling only), the master palette, the type system, the tokens. No default fonts, no stray colors, no unaligned sprites, no placeholder boxes, no lorem.
- **Look at your own work.** Capture screenshots with Playwright at 390px and 1280px, light and dark chrome, and for canvas scenes capture frames at several timestamps. Open them with the image Read tool and critique them against the reference collage like an art director: composition, hierarchy, spacing rhythm, palette harmony, edge pixels, text legibility, contrast, empty/loading/error states. Fix and re-shoot at least three rounds. Keep the final shots in docs/design/shots/<ws>/.
- **Run the review panel before you hand off**: spawn read-only reviewer sub-agents (layout and phone, type and rhythm, colour and states, motion and access, message and action, plus a pixel-art/scene reviewer) using docs/design/review-rubric.md; merge their findings; fix everything high and medium; re-run.
- **Motion** follows docs/specs/08-village-motion.md exactly: gate by frequency and purpose, the three curves only, transform/opacity only in the DOM, walking never eased, words never move for style, Calm mode and prefers-reduced-motion variants, pause when the tab is hidden. Verify by playing at 0.25x and stepping frames.
- **Accessibility and input**: keyboard-only play works, every scene has a text alternative, focus is visible, tap targets are at least 44px, contrast meets the rubric.
- **Performance**: 60 fps on a mid-range phone for the village, no layout shift, lazy-load Phaser, small atlases.
